## ПРИНЦИПЫ РАБОТЫ

### 1. Принцип «Таблицы ДО кода»
ИИ хорошо структурирует по шаблону. Все компоненты, зависимости, типы → в таблицы ДО написания. При написании — копировать из таблиц, не изобретать заново.

### 2. Принцип доказательств
Нет библиотеки в таблице зависимостей — её не существует в этом проекте. Нет типа в таблице сигнатур — функция не написана правильно.

### 3. Принцип явности (Zen of Python)
> *«Explicit is better than implicit»*
Ключевые решения — прямым кодом. Не магией, не хаками, не «умными» однострочниками там, где нужна ясность.

### 4. Принцип медленного режима
- **ПЕРЕД** написанием: создать таблицы из PYTHON_СТРУКТУРА.md
- **ВО ВРЕМЯ**: сверяться с таблицами при каждом импорте, типе, функции
- **ПОСЛЕ**: прогнать через чеклисты верификации

### 5. Принцип безопасности по умолчанию
Любой код, работающий с внешними данными (ввод пользователя, файлы, БД, API) — сначала валидируется, потом используется.

## СПЕЦИФИКА PYTHON-НИШИ

### Что отличает хороший Python-код

- **Читаемость важнее краткости.** Код читают люди. Однострочник, требующий 10 секунд осмысления — плохой однострочник.
- **Явные типы везде.** `def process(data)` — плохо. `def process(data: list[dict]) -> pd.DataFrame` — хорошо.
- **Исключения — не враги.** Обрабатывать конкретные исключения (`except ValueError`), а не всё подряд (`except Exception`).
- **Конфигурация отдельно от логики.** Никаких магических чисел и строк прямо в коде.
- **Один модуль — одна ответственность.** `utils.py` на 800 строк — это не utils, это свалка.

### Частые ошибки ИИ в Python

- **Несуществующие методы:** `df.filter_by(...)` у Pandas, `list.find(...)` — ИИ изобретает API.
- **Устаревший синтаксис:** `% форматирование`, `open()` без `with`, `print` без скобок в Python 3.
- **Игнорирование GIL:** многопоточность там, где нужен multiprocessing или asyncio.
- **Мутабельные дефолты:** `def f(lst=[])` — классическая ловушка.
- **Голые except:** `except:` без указания типа — запрещено.
- **Небезопасная десериализация:** `pickle.loads(user_input)` — уязвимость.
- **Хардкод секретов:** `API_KEY = "sk-1234"` прямо в коде.
- **Отсутствие `__all__`** в публичных модулях.
- **f-строки в SQL-запросах:** `f"SELECT * FROM {table}"` — SQL injection.

## ПРАВИЛА БЕЗОПАСНОСТИ (критические)

### ЗАПРЕЩЕНО ВСЕГДА:
```python
# ❌ SQL injection
query = f"SELECT * FROM users WHERE name = '{user_input}'"

# ❌ Хардкод секретов
API_KEY = "sk-abc123"
PASSWORD = "admin123"

# ❌ Небезопасная десериализация
data = pickle.loads(user_data)

# ❌ Выполнение пользовательского ввода
eval(user_input)
exec(user_input)

# ❌ Голый except
try:
    something()
except:
    pass

# ❌ Мутабельный дефолт
def process(items=[]):
    ...
```

### ОБЯЗАТЕЛЬНО:
```python
# ✅ Параметризованные запросы
cursor.execute("SELECT * FROM users WHERE name = ?", (user_input,))

# ✅ Секреты из окружения
import os
API_KEY = os.environ["API_KEY"]

# ✅ Конкретные исключения
try:
    result = int(user_input)
except ValueError as e:
    logger.error("Invalid input: %s", e)
    raise

# ✅ Иммутабельный дефолт
def process(items: list | None = None) -> list:
    if items is None:
        items = []
    ...
```

## КРИТИЧЕСКИЕ ПРАВИЛА

### ✅ ОБЯЗАТЕЛЬНО
- Прочитать ВСЕ Python-файлы системы перед началом
- Создать таблицы 2.1, 2.2, 2.3 ДО написания кода
- Type hints на каждой функции/методе
- Docstring на каждой публичной функции/классе
- `with` для работы с файлами и соединениями
- Параметризованные запросы для SQL
- Секреты только через переменные окружения

### ❌ ЗАПРЕЩЕНО
- Изобретать несуществующие методы библиотек
- f-строки в SQL-запросах
- Хардкод API-ключей, паролей, токенов
- Голые `except:` без типа исключения
- Мутабельные аргументы по умолчанию
- `eval()`/`exec()` с пользовательским вводом
- Магические числа без именованных констант
- God-функции длиной > 50 строк (декомпозировать)
- Импорты внутри функций (кроме отложенных с обоснованием)

## ЧЕКЛИСТ ПЕРЕД СДАЧЕЙ КОДА

### Структура
- [ ] Таблица 2.1 (компоненты) заполнена и соответствует коду?
- [ ] Таблица 2.2 (зависимости) — все импорты из таблицы, нет лишних?
- [ ] Таблица 2.3 (сигнатуры) — все функции соответствуют?

### Качество кода
- [ ] Type hints на всех публичных функциях/методах?
- [ ] Docstrings на всех классах и публичных функциях?
- [ ] Нет магических чисел (только именованные константы)?
- [ ] Нет дублирования логики (DRY)?
- [ ] Каждая функция делает одно (SRP)?
- [ ] Функции не длиннее 50 строк?
- [ ] PEP 8 соблюдён (именование, отступы, длина строк ≤88)?

### Безопасность
- [ ] Нет хардкод-секретов в коде?
- [ ] Нет f-строк в SQL-запросах?
- [ ] Нет `eval()`/`exec()` с внешними данными?
- [ ] Нет голых `except:`?
- [ ] Нет `pickle.loads()` с пользовательскими данными?
- [ ] Все входные данные валидируются перед использованием?

### Надёжность
- [ ] Все внешние вызовы (API, БД, файлы) в `try/except`?
- [ ] Ресурсы (файлы, соединения) закрываются через `with`?
- [ ] Логирование через `logging`, не через `print`?
- [ ] Нет вложенных циклов O(n²) без обоснования?
